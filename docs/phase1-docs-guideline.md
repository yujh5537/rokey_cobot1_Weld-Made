# 1차(스캔) 담당분 정리 가이드라인 — 문서 · 산출물 · 발표자료

작성: 병후 · 2026-09-23. 대상: 현지 · 의석 · 학민 · 병후. 기간: 연휴(9/24~9/28), **문서를 앞에, phase 2 개발을 뒤에.**

## 왜 하나
1. **발표 자료의 원천** — 발표(15~20 분, pptx)는 각자 파트 슬라이드를 직접 만들고 병후가 합칩니다. 슬라이드에 넣을 그림 · 수치 · 문장이 먼저 문서에 있어야 합니다.
2. **최종 산출물** — 레포의 `docs/`가 프로젝트의 결과물입니다. 지금 흩어져 있는 것(README · 시험 보고 · PR 본문 · 슬랙)을 한 자리에 모읍니다.
3. **이어받기** — phase 2 와 그 뒤의 사람이 "왜 이렇게 됐는지"를 코드 없이 알 수 있게.

### 1. 패키지 README
기준 틀은 `ws_cobot1/src/scan_manager/README.md`(파일 표 → 동작 → 파라미터 → 테스트). 있어야 하는 것:
- 파일별 역할 표(rclpy 쓰는지 표시), 노드가 발행 · 구독 · 제공하는 것(계약 문서 절 번호로 링크)
- 파라미터 표: 이름 · 출발값 · 실측값(있으면) · 근거(보고서 · PR)
- 실행 · 테스트 명령(복사해서 돌아가는 것만)
- 알려진 문제(열린 이슈 번호)
mqtt_bridge 는 README 가 없으니 새로 씁니다. 코드에서 이미 바뀐 동작이 README 에 옛 대로 남아 있으면 고칩니다.

### 2. 파트 정리 문서 `docs/phase1/<파트>.md` — 목차 고정
```markdown
# <파트> 정리 (1차 스캔, 2026-09-18 ~ 09-23)
담당: · 관련 이슈: #.. · 관련 PR: #..

## 1. 맡은 것과 범위        무엇을 만들었고 무엇은 안 했나 (2~5 줄)
## 2. 설계                 핵심 결정 3 개 안팎: 무엇을 · 왜 · 대안은 무엇이었나 (ADR · PR · 계약 절 링크)
## 3. 구현                 자료 흐름 또는 상태 그림 1 장 + 핵심 알고리즘 · 절차 한 단락씩
## 4. 시험 · 실측           설계 출발값 vs 실측값 표, KPI(BRD 9장) 대비 결과. 근거는 docs/test-reports 링크
## 5. 문제와 해결           실기에서 겪은 것 3~5 개: 증상 → 원인 → 조치 → PR 번호 → 교훈 한 줄
## 6. 남은 문제 · 한계       열린 이슈, 못 잰 것, 가정
## 7. 발표 후보             슬라이드에 쓸 그림 · 수치 · 한 문장 (3~7 개)
```
- 5장이 가장 중요합니다. 발표 "문제와 해결" 장과 회고의 원천입니다. 사실만 적고 평가는 넣지 않습니다.
- 4장의 수치는 **실측 · 설계 출발값 · 계산값을 구분**해 적습니다(1차 관례). 출처 없는 숫자는 쓰지 않습니다.

### 3. 발표 슬라이드
- 목차 · 배분은 **`docs/presentation/outline-v1.md`**(병후 · 9/24 확정). 양식 5 장 고정, 15~20 분, 28~32 장.
- `docs/presentation/template.pptx`(양식에서 안내 2 장을 지우고 표지를 채운 사본)를 복사해 `docs/presentation/slides-<파트>.pptx` 로 자기 파트만 만든다. 병후가 합친다.
- 슬라이드 한 장 = 제목(주장 한 문장) + 그림 · 표 1 개 + 글머리 3 줄 이하. 발표 대사는 슬라이드 노트에 3~5 문장.
- 배분(outline-v1 요약): 학민 3~5 장(01-④ 장비, 04-② 기준 확정, 04-⑧ 문제 1), 현지 4~6 장(04-③ 접촉 · 안전, 04-⑥ 실기 결과 · KPI, 04-⑧), 의석 4~5 장(04-⑤ HMI · 연동 2, 04-⑧, 04-⑩ 영상은 현지와), 병후 나머지.
- 슬라이드와 별도로 병후에게 보낼 것: 05 완성도 점수(10 점)와 이유, 개인 한 줄, 02 표의 자기 담당 한 줄.

### 4. 그림 · 데이터
- `docs/presentation/assets/<파트>/` 에 png · drawio · 캡처. 원본 CSV · bag 은 옮기지 않고 `docs/test-reports/data/` 경로만 문서에 적습니다.
- 그림의 이름(노드 · 토픽 · 파라미터)은 계약 문서와 같은 이름을 씁니다.

### 5. 최종 산출물(강사 요구 9 종) — 담당 항목
`docs/deliverables/README.md` 2 절의 표대로 **자기 담당 항목**을 `docs/deliverables/0N-<이름>.md`(+ 그림)로 만들고, 구글 드라이브 `deliverables` 폴더에 pdf · png 로 등록한다. 담당: 시스템 아키텍처 · 인터페이스 정의서 · 노드 구조도 · BRD = 병후 / 네트워크 구성도 = 현지 + 의석 / 동작 순서도 = 현지 / 하드웨어 구성 · 예외 · 오류 · 위험 · 안전 = 학민 / HMI 화면 구성 = 의석. 제출물 4 종: 영상 의석 · 현지 · 소스 zip 현지 · Readme 의석 · pdf 병후.

## 형식 · 제출
- 한국어 md. 링크는 레포 상대경로. 사진 · 캡처에 날짜.
- **사람당 PR 1 개**(`docs-p1-<이름>`), 4 종을 한 PR 에 넣어도 됩니다(문서라 15 파일 규칙 예외). 리뷰는 병후. 슬라이드 pptx 는 같은 PR 에 커밋합니다.
- 다른 사람 담당을 설명해야 하면 그 사람 문서로 링크하고 여기서는 한 줄만.

## 자기 점검 (PR 올리기 전)
- [ ] 수치마다 출처(보고서 · PR · 로그 파일)가 있다
- [ ] 실측값 · 설계 출발값 · 계산값이 섞여 있지 않다
- [ ] 그림 · 표의 이름이 계약 문서와 같다
- [ ] 5장의 "문제와 해결"이 사실(증상 · 원인 · 조치)로만 되어 있다
- [ ] README 의 실행 · 테스트 명령을 실제로 돌려 봤다

## phase 2 개발과의 순서 (권고)
연휴 초반(9/24~26)에 1 · 2 를 끝내고 3 을 내면, 병후가 후반(9/27~28)에 종합할 수 있습니다. phase 2 파트 개발은 그 뒤 비중을 높입니다. 새 코드는 **HLD → DD → pseudo → real code** 순서를 권합니다(병후 브리핑은 필요 없고 자체 점검). 다른 사람 담당과 통신하거나 영향을 주는 변경(계약 · 인터페이스 · 공유 파라미터)은 먼저 PR 로 확인받고, 그 밖은 유연하게 진행합니다.
