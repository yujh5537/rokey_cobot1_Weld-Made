# ADR-0004: 안전 감사 후 팀 결정 10건

- 날짜: 2026-09-22 / 결정한 사람: **팀 합의(9/22 회의)** / 상태: 채택
- 후속 합의: 2026-09-23 PR #161 리뷰(#132 처리 · M1 보류 · 재시작 첫 모션 · 정지 사유 판정)

## 배경

T06 안전 감사(`docs/test-reports/safety-audit_20260921.md`, PR #144)와 그 검토
(`docs/test-reports/safety-audit-review_20260922.md`)가 팀 결정이 필요한 항목 10건을 §7 에 정리했다.
검토 보고서는 각 항목에 추천을 달았지만 결정 권한은 없다. 이 ADR 이 결정이다.

검토 보고서의 전제 세 가지를 그대로 받는다.
① MVP 로 F1~F5 가 끝까지 도는 것이 최우선이다. ② 통신 지연 자체는 보류한다.
③ 모든 실습에서 사람이 티치펜던트를 들고 감시한다.

## 결정

| # | 항목 | 검토 보고서 추천 | 결정 |
|---|---|---|---|
| 1 | ERROR 재시작 정책 | ② 사유별 허용 | **②.** `SAMPLE_STALE(403)` · `ROBOT_STATUS_LOST(404)` · 정지 미확인만 RESET 뒤 RESUME 을 허용한다. 물리적 위험은 새 START |

추천과 다르게 정한 것은 **4번**(실험 뒤 결정 → 지금 REL 유지 + 세 값 표시)과 **8번**(15 N 으로 낮춤 →
30 N 유지)이다. 4번은 스텝 모드가 실기 기본이 되어 REL 이 더는 주 경로가 아니므로 저울 실험을 기다릴
이유가 없어졌다. 8번은 스텝 모드가 자체 한계 12 N 으로 먼저 멈추므로 전역 한계를 낮출 필요가 없고,
전역 한계를 낮추면 `force` 경로와 `OP_DESCEND` · `OP_MOVE_TO` 의 여유까지 같이 줄어든다.

## 근거와 검토한 대안

**1 · ERROR 재시작.** 현행은 `ERROR` 에서 RESUME 을 전부 `NOT_SUPPORTED` 로 거절해 F4(안전 정지 뒤
복구)가 성립하지 않았다. 반대로 모든 안전 사유를 허용하면 오염된 기준으로 재개할 수 있다. 세 사유
(403 · 404 · 정지 미확인)는 **측정값이 오염되지 않는** 사유다 — 샘플이 끊겼거나 정지를 확인하지
못했을 뿐, 탐침이 무언가에 세게 닿지 않았다. `OVER_FORCE` · `DROP_LIMIT` 은 탐침 · 부재가 상했을 수
있어 사람이 보고 새로 시작해야 한다. **목록에 없는 새 사유는 자동으로 불허**다(allowlist).

"정지 미확인"은 그때까지 `ROBOT_STATUS_LOST(404)` 로 보고되고 있었다. 두 사유 다 허용 목록에 있어
동작은 같지만, **허용 여부를 사유로 판단하는 규칙에서 사유가 섞여 있으면 안 된다.** 그래서
`STOP_UNCONFIRMED(407)` 를 새로 두고 갈랐다.

**2 · 하강 제한.** 1차 · 2차가 같은 값이면 잡음 한 샘플로도 2차가 먼저 걸려, 1차가 정상 동작인데
래치부터 걸린다. 대안 ③(2차 `confirm_n = 2`)은 시간으로 늦추는 것이라 하강 속도에 따라 실제 여유가
달라져 기각했다. `drop_limit_m` 자체를 노드마다 다르게 두는 안은 `SetConfig` P03 이 두 노드에 **같은
값**을 보내므로 설정을 한 번만 바꿔도 여유가 사라져 기각했다. safety_monitor 전용 파라미터
`drop_limit_margin_m`(계약 이름 아님, `ScanConfig` 에 없음)으로 둔다.

**9 mm 는 어디서 왔나.** 탐침 길이를 손으로 재어 정한 **간섭 없는 안전 거리**다 — 2차가 걸릴 때까지
내려가도 탐침 · 부재가 상하지 않는 거리이며, 따라서 상한이다. 여유 4 mm 는 9 에서 1차 5 를 뺀 값이고,
여유가 먼저 정해진 것이 아니다. **하한은 미확인으로 남는다**: 1차가 정지를 끝낼 때까지의 하강
오버슈트가 여유를 넘으면 1차가 정상 정지할 때마다 2차가 래치되어 #53 이 그대로 재발한다.
샘플 주기 약 94 ms(10.6 Hz)와 물리 정지 1 s 사이에 z 가 얼마나 더 내려가는지는 아직 재지 않았다.

**선행 조건이 기준 z 통일이다.** robot_manager 는 실행 직전의 마지막 위치를, safety_monitor 는
`OP_SLIDE` 첫 샘플을 기준으로 잡고 있었다. 순응 제어를 켜면 z 가 약 0.7 mm 올라오므로 두 기준이
그만큼 어긋난다. 기준이 어긋난 채 임계값만 바꾸면 여유가 의미를 잃는다. robot_manager 가
**자기가 `OP_SLIDE` 로 발행한 첫 유효 샘플의 z** 를 쓰게 해 같은 메시지의 같은 값으로 맞췄다.

**3 · 최신성.** #130 에서 정지 중 약 3 s 마다 316~365 ms 공백이 반복돼 goal 의 약 40 %가
`SAMPLE_STALE` 로 멈췄다. 정지가 정상 동작을 막는 상태였다. 500 이면 기록된 공백 14개 중 687 ms 하나만
걸린다. **687 ms 공백이 실제로 있었으므로 500 도 완전하지 않다.** 그래도 700 으로 더 올리지 않는 이유는
공백 동안에는 1차 · 2차가 모두 앞을 보지 못하고, 그 시간이 길수록 하강 제한 감시도 같이 늦기 때문이다.
데이터가 더 쌓이면 700 을 검토한다. #130 의 근본 원인이 풀리면 300 으로 되돌린다.

**4 · force/REL.** `slide_target_force_n` 은 `DR_FC_MOD_REL` 이라 "설정한 증분"이다. 실제 누름은 SLIDE 를
어디서 시작하느냐에 따라 달라진다(9/22 실기 방향별 1.5~8.6 N). 그래서 "3 N 으로 설정했다"와 "3 N 으로
눌렀다"를 같은 자리에 쓰면 안 된다. 세 값을 각각 싣고 합은 **추정**이라고 이름에 박는다. 힘 제어 중의
조회 Fz 는 1 N 안팎이 나와 실측으로 쓰면 오히려 오해를 부르므로 "실측 누름"이라는 값은 만들지 않는다.
전자저울 실험(검토 보고서 M6)은 여전히 유효한 후속이지만, 실기 기본이 `step` 이 되어 선행 조건이 아니다.

**5 · EDGE.** PR #160 이 9/22 실기에서 네 방향을 반복 0.03 mm 로 끝냈다. 이 PR 은 그 로직을 다시 쓰지
않는다. 필요한 것은 회귀 방지와 새 안전 정책과의 통합뿐이다.

**6 · 중지 KPI.** 접촉 중에는 43 N/mm × 3 mm/s = 약 129 N/s 라 3 N 에서 탐침이 밀리는 43 N 까지 0.31 s 다.
물리 정지에 3 s 를 주면 받아들일 수 없는 영역이 생긴다. 반면 "시스템이 정지를 확인하고 STOPPED 를
표시하기까지"는 정지 확인 창 + 상태 주기 + `wait_still` 이 겹쳐 1 s 로는 현실적이지 않다. 그래서 둘로 나눈다.
BRD 9장의 "작업 중지 반응 시간 1초 이내"는 **물리 정지**를 뜻하며 그대로 둔다(문서를 고치지 않았다).

**7 · 안전복귀.** #130 에서 **올림이 실패했는데 HOME 이 나간 사례가 2회** 있었다. 탐침이 부재에 닿은 채
관절 복귀가 나가면 탐침 · 부재가 상한다. 위치를 모르면 올릴 목표를 만들 수 없으므로 사람이 조그한다.
`OVER_FORCE` · `DROP_LIMIT` 으로 끝났으면 이미 무언가에 세게 닿은 뒤이므로 보수적으로 손상 가능으로 본다.
안전복귀가 중지 · 실패를 자동으로 잇지 않는 것은 그대로다(CLAUDE.md 규칙 3).

**8 · 과대 외력.** 사람의 반응(1~2 s)보다 힘 상승이 빠른 영역은 SW 한계만이 막는다. 그래서 한계를 **올리지**
않는다는 원칙은 유지한다. 낮추는 것은 다른 문제다 — 스텝 모드가 12 N 에서 스스로 멈추므로 전역 한계를
낮춰 얻는 것이 없고, 낮추면 `force` 경로와 이동 모션의 여유가 같이 줄어 거짓 정지가 는다.
**12 N 을 30 N 으로 올리지도 않는다.** 올리면 스텝 모드의 자체 보호가 사라진다.

**9 · 디바운스.** `get_tool_force` 값은 약 10 Hz 로만 갱신되는데 robot_manager 는 약 43 Hz 로 조회해
발행한다. 그래서 "연속 3 샘플"은 사실상 "측정 1회 + 약 44 ms 대기"다. 이 사실을 계약에 적되 값은 바꾸지
않는다 — 실기에서 이 값으로 검증된 기록이 있고, 바꾸면 임계와 편향 보정을 다시 재야 한다.
"값 변화 3회"는 오프라인 계산에서 판정 순간 참 힘 중앙 34.8 N · 최대 40.6 N 이 나와 **쓸 수 없다.**

**10 · #141 기준점.** 새 탐침 하강점과 `base_to_fixture` 가 2.96 mm 어긋나 있었다. 작업환경을 물리적으로
다시 구성해 해결했다. **수치는 바꾸지 않는다** — 확정된 새 실측값이 레포 · 이슈 · PR 어디에도 없다.
없는 값을 추측해 넣지 않는다. 실측이 나오면 `units-frames.md` 와 real.yaml 을 같은 PR 에서 고친다.

## 후속 합의 (2026-09-23, PR #161 리뷰)

**결정 5 에 딸린 #132 힘 꺾임 EDGE — (a) 꺼 둔 채 문서에 명시한다.**
지금 실기 기본은 `step` 모드이고 `force` 는 sim 경로다. `edge_force_drop_n` 은 꺼 둔다(0.0).
코드 제거(대안 c)는 하지 않는다 — `force` 모드는 계약에 남아 있고 sim 이 쓴다. 지금 지우면 되돌리기가
비싸다. 편향 보정 확인 뒤 `force` 전용으로 켜는 길(대안 b)도 막지 않는다. **`force` 모드를 영구히
금지하는 결정이 아니다.**

**M1 (tare 허용치 `tare_tolerance_n` 0.3 → 0.5 N) — 보류한다.**
지금 올릴 근거가 없다. 감사 M1 의 데이터가 전부 0.3 아래다 — 9/20 CSV RMS 중앙 0.047 N · 최대 0.199 N,
9/21 tare 3 회 0.143 · 0.214 · 0.110 N. 허용치는 **`TARE_UNSTABLE` 이 실제로 난 세션에서만** 올리고,
그때의 RMS 와 날짜를 yaml 주석에 같이 남긴다.

**재시작의 첫 모션 — 지금 위치 기준으로 바꾼다(계약 7.6 신설).**
기록된 중단 좌표를 절대 좌표 목표로 쓰고 있었다. `STOP_UNCONFIRMED(407)` 은 정의상 정지를 확인하지
못한 것이라 기록 좌표가 지금 자리가 아닐 개연성이 허용 3 코드 중 가장 높다. 안전복귀(7.5 ①)와 같은
규칙을 쓰고, 위치를 모르면 **RESUME 접수 때 거절한다**(실행 중에 실패하면 실패 기록에 `resumed_at` 이
찍혀 다시 이을 기회가 사라진다). `home_pose_max_age_s` 는 두 경로가 함께 쓰므로 `pose_max_age_s` 로
이름을 바꿨다.

**요청하지 않은 정지의 사유 — `Result.reason_code` 를 먼저 읽는다.**
`/safety/status` 의 도착 순서에 기대면 사유가 `ROBOT_ERROR(204)` 로 뭉개져 손상 의심 판정이 새어
나갔다. safety_monitor 가 `/robot/stop` 의 `reason` 에 205 · 400 을 싣고 robot_manager 가 그것을
`Result.reason_code` 로 돌려주므로 도착 순서와 무관해진다. 래치 사유도 같이 보지만 그것만으로는
부족하다 — 사람이 `/scan/home` 전에 `/safety/reset` 을 누르면 다시 204 로 샌다.

**별도 PR 로 뺀 것.** 재접촉 검증(결정 1 을 대체하는 설계 변경) · M7(정지 요청 우선 처리) ·
M11(HOME 도착 관절각 검증). 주제가 서로 다르고, 이 PR 이 이미 크다.
