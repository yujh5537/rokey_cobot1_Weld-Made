# **1. 비즈니스 목표**

로봇이 카메라 없이 단일 직육면체 부재를 직접 만져 형상 좌표를 얻고, 윗면의 외곽 엣지와 경로 후보를 생성한다. RG2는 무센서 탐침을 단단히 파지하고, M0609의 관절 토크 기반 외력 추정과 TCP 위치 정보로 접촉·엣지를 판단한다. MVP는 형상·좌표 획득과 과정 시각화의 실증 단계이다. 단일 블록의 외곽을 두 부재 사이의 실제 용접 이음으로 판정하지 않으며, 실행 가능한 용접 경로나 토치 자세까지 검증한 결과로 표현하지 않는다. 장기적으로는 이음 식별과 용접 조건 검증을 추가하여 용접 자동화로 확장한다.

## **1.1 문제 정의**

- 협동로봇 용접은 작업자가 로봇 끝단을 잡고 용접 시작점·끝점으로 옮겨 위치를 기록하는 직접교시에 의존한다 [E4][E13]. 품종이 바뀌면 이 작업을 다시 해야 한다.

- 고정식 산업용 로봇은 다품종 소량 생산이 잦고 공간이 좁은 중소 제조 현장에 적용하기에 유연성이 떨어진다는 지적이 있다 [E1]. 중소 현장의 용접 자동화는 “품종 교체를 얼마나 가볍게 넘기느냐”의 문제이다.

- 이 일을 맡을 사람이 부족하다. 뿌리산업 종사자의 68.2%가 40대 이상이며 [E2], 10인 미만 뿌리 제조업체의 89.3%가 인력 부족을 호소하고 업체당 평균 종사자는 2.8명이다 [E3].

- **우리의 가설:** 다품종 소량 중소 제조사에서 “품종 교체 시 재티칭”이 협동로봇 용접의 가장 큰 운영 비용이다.

- **가설의 한계(인정):** 협동로봇 용접은 용접사가 15~30분에 셋업을 바꾼다는 업계 주장도 있다 [E13]. 따라서 1회 티칭 시간은 사실로 단정하지 않고 가정값으로 두며, 이 값이 작을 때 사업성이 무너지는 것까지 1.6절에 제시한다.

## **1.4 로봇팔로 자동화할 수 있는가 — MVP 탐색 절차로 본 실현 가능성**

접촉으로 이음 위치를 찾는 원리는 이미 검증되어 있다. 용접 로봇의 와이어 터치센싱은 조인트당 최소 2회(코너는 3회)의 접촉으로 이음을 찾는 상용 기술이다 [E5][E8]. 우리는 이 원리에서 **감지 수단을 통전에서 기계적 접촉으로**, **결과물을 오프셋에서 형상 생성으로** 바꾼다. MVP 절차는 다음과 같다.

| **#** | **절차** | **로봇 동작 (DSR_ROBOT2)** | **판정** | **획득값** |
| --- | --- | --- | --- | --- |
| 1 | 윗면 높이 획득 | 원점 상공에서 팁을 저속·등속으로 수직 하강한다(amovel, −z). | 외력 임계 초과 → 정지 | z_top |
| 2 | 모서리 4점 획득 | 윗면을 가볍게 누른 상태(순응 제어 + −z 목표 힘)로 +x 방향으로 직선 이동한다. 원점으로 돌아와 −x, +y, −y를 반복한다. | z 급강하(접촉 소실) → 정지, 좌표 기록 | x⁺, x⁻, y⁺, y⁻ |
| 3 | 윗면·외곽 엣지·경로 후보 생성 | 로봇 동작 없음(계산). | — | 꼭짓점 4개 (x±, y±, z_top), 외곽 엣지·경로 후보 4개 |
| 4 | 직육면체 완성 | 로봇 동작 없음(계산). 확정한 지지면 높이로 투영한다. 작업대 지지면을 z=0으로 정한 경우 z=0을 쓴다. | — | 꼭짓점 8개, 모서리 12개 |

**접촉 감지 방식의 설계 결정: RG2 제품 설명 [E17]과 드라이버 소스 검토 [E18]를 근거로, RG2는 탐침 파지에 사용하고 접촉 판정은 B. 로봇 내장 힘 감지(robot_force)로 수행한다. C. 가상 접촉(sim)은 개발·시험용이다. A. RG2 쐐기·폭 변화 방식은 가정값에 따른 이론 검토 이력만 남기며, 실제 실험을 수행한 적이 없고 향후 구현·실험도 계획하지 않는다. M0609의 3 N 접촉 판정 역시 본 프로젝트의 실기 검증 이력으로 인정하지 않는다.**

| **입력원** | **접촉 판정 방식** | **근거 / 한계** | **지위** |
| --- | --- | --- | --- |
| **B. 로봇 내장 힘 감지 (robot_force)** | 접촉 발생: get_tool_force()의 외력 크기가 기준값 대비 임계(3~5 N에서 시작)를 넘으면 접촉. 접촉 소실: −z로 가볍게 누르던 팁이 모서리에서 떨어지며 생기는 **mm 단위의 z 급강하**(get_current_posx, check_position_condition)를 주 신호로, 외력 감소를 보조 신호로 쓴다. | 두산 API가 제공한다 [E10]. | A. RG2 폭 변화 (rg2) | 팁 하중을 쐐기형 홀더의 횡방향 힘과 RG2 폭 변화로 변환하는 개념이다. 가정값을 둔 이론 검토만 수행하였다. | 실제 폭 변화·역구동·자기잠김·검출 성능은 미확인이다. 실험 이력이 없고 향후 구현·실험 계획도 없다. | 이론 검토 이력 구현·실험 제외 |

**B를 기본으로 정한 이유**

| **판단 기준** | **검토 결과** |
| --- | --- |
| **B의 인프라는 어차피 필요하다** | 모서리 탐색은 윗면을 누른 채 이동하므로 task_compliance_ctrl()과 set_desired_force()가 필수이고, 과대 외력(30 N) 감시에도 get_tool_force()가 필요하다. A는 B를 대체하지 못하고 일만 더한다. |
| **A의 감도·복귀 특성은 가정에 민감하다** | 계산 가정: 대칭 쐐기, 마찰계수 μ=0.3, 팁 하중 5 N, 쐐기 반각 30° 또는 15°. 이 조건의 개략 계산 결과는 약 2.4 N / 4.0 N이며 마찰각은 약 16.7°이다. 이는 실측값이 아니다. 제품 설명의 최소 파지력 3 N [E17]과 쐐기 횡력의 직접 비교에는 힘 정의·전달 구조·역구동 특성 확인이 필요하므로, 실제 폭 변화나 자기잠김의 발생을 단정하지 않는다. |
| **A의 정확도 영향은 미검증이다** | 좌표를 로봇 위치값에서 얻으려면 탐침 팁과 TCP의 관계가 안정적이어야 한다. A에서 팁이 0.3~0.6 mm 움직인다는 값은 예시 가정이며 실측값이 아니다. 쐐기의 유격·히스테리시스가 정확도에 미치는 영향도 미검증이다. B는 탐침을 고정하는 구조로 설계한다. |
| **B의 판정 신호를 설계상 선택한다** | B는 외력 변화와 TCP z 변화를 판정 신호로 사용한다. A의 폭 값 단위는 드라이버 소스 근거 [E18]이며 실제 검출 분해능이나 지연 측정값이 아니다. 두 방식의 신호 품질을 실험 비교한 이력은 없다. |
| **구현 범위를 B와 sim에 집중한다** | 팀의 M0609 3 N 접촉 판정 실기 검증 이력은 없다. B는 기존 로봇 API를 활용하는 설계 선택이며 성능은 향후 검증한다. RG2 쐐기 방식은 이론 검토로 종료하고 제작·구현·실험에 일정을 배정하지 않는다. |

**API 설명과 확인 수준의 구분**

매뉴얼 설명 [E10]: API의 기능·인자·주의사항에 관한 근거이다. DRL 매뉴얼의 함수가 ROS2 Python 래퍼에도 같은 이름으로 노출되거나 실제 장비에서 같은 조건으로 동작한다는 뜻은 아니다.

소스 코드 확인 [E18]: 기존 문서가 검토한 저장소의 메시지 필드, 함수·서비스 정의, 발행 설정에 관한 근거이다. 설정상 50 Hz와 실제 수신·처리 주기의 실측값은 구분한다.

실행환경 확인 [E19]: 팀은 실제 사용 PC에서 패키지·서비스 목록과 API 호출을 확인하였다. 다만 항목별 성공·실패 결과, 패키지 버전, 호출 로그는 본 문서에 아직 정리되지 않았다. 아래 API별 설명의 근거는 매뉴얼·소스이며, 모든 API 호출의 성공을 일괄 확정하지 않는다.

실기 성능 검증: 실제 PC의 API 확인은 탐침 접촉 검출·정확도·반복성 검증과 별개이다. M0609 3 N 접촉 검출 실험은 수행 이력이 없는 것으로 정리한다. RG2 쐐기 방식은 미실험이며 향후 실험 계획도 없다.

B 구현 계획: 아래 설정값은 개발 출발값이며, 실제 탐침과 작업 환경 구성 후 실측으로 조정한다.

- 툴 무게와 무게중심(RG2 + 탐침)을 정확히 등록한다. 하강은 저속·등속으로 하고(가감속 관성력이 외력으로 읽히는 것을 피한다), 임계값은 3~5 N에서 시작해 실측으로 조정한다.

- 매뉴얼상 set_external_force_reset()은 DRL API이다 [E10]. 기존 소스 검토에서는 해당 함수가 ROS2 Python 래퍼에 노출되지 않은 것으로 정리하였다 [E18]. 구현은 비접촉·정지 상태에서 1~2초 수집한 get_tool_force() 평균을 기준값으로 사용하는 안을 유지한다. drl_script_run() 경유 리셋 호출의 성공 여부는 확인 항목으로 남긴다.

- 매뉴얼상 set_desired_force()에는 DR_FC_MOD_REL을 사용하고, check_force_condition()은 방향 없이 크기를 비교하므로 방향 판정에는 get_tool_force()의 성분값을 사용한다 [E10]. 기존 소스 검토에서 Python stop() 노출이 확인되지 않아 [E18], 이동 정지는 motion/move_stop(DR_QSTOP)을 사용하는 구현 계획이다. 실제 PC 확인 이력은 [E19]와 구분해 기록한다.

- **좌표의 출처:** 힘은 “닿았다/떨어졌다”의 트리거일 뿐이고, 좌표는 그 순간 로봇의 위치값(get_current_posx)에서 나온다. 탐침은 홀더로 TCP에 단단히 고정되며, M0609의 반복정밀도는 ±0.03 mm이다 [E4].

- 본 문서의 x·y·z와 z_top은 작업대 좌표계에서 해석한다. 로봇 Base에서 읽은 위치값과의 변환, TCP 기준점 및 실제 원점은 환경 세팅 후 확정한다. 로봇 홈위치(시작위치)와 작업대 원점은 구분한다.

- **모서리 편향 보정:** z 급강하 판정을 쓰므로, 반지름 r의 구형 팁이 모서리를 지나 δ만큼 내려갔을 때 소실로 판정하면 팁 중심은 모서리를 √(2rδ−δ²)만큼 지나친 상태이다. 여기에 (이동 속도 × 판정 지연)을 더한 값을 빼서 보정한다. 예: r=3 mm, δ=0.5 mm, 10 mm/s, 지연 40 ms이면 약 1.7+0.4=2.1 mm(설계 출발값, 기준 블록으로 실측 보정).

- **배치 가정의 영향:** 변이 축과 평행하면 부재 중심이 원점에서 벗어나도 네 모서리 좌표는 참값으로 측정된다(원점이 윗면 위에만 있으면 된다). 반면 회전에는 민감하여, 부재가 θ만큼 돌아가 있으면 꼭짓점이 축마다 약 (변 길이/2)×tanθ씩 어긋난다. 예: 100 mm 변, 2° → 축당 약 1.7 mm(거리로 약 2.5 mm).

- **선행 연구:** 외부 센서 없이 접촉과 로봇 위치값만으로 실환경 평균 0.42 mm의 정합을 보인 연구가 있다 [E15].

# **2. 프로젝트 범위**

## **포함 범위 (In Scope) — 이번 교과 프로젝트에서 반드시 시연하는 MVP**

- 대상: 고정 배치한 단일 직육면체 부재. 작업자가 정해진 배치 기준에 맞추고 변을 작업대 x·y축과 평행하게 놓는다. 작업대 좌표계·Base 관계, TCP, 지그와 실제 지지면 및 z=0 기준은 물품 도착 및 환경 세팅 후 확정한다(6장). 홈위치는 로봇의 시작위치이며 작업대 원점과 동일하다고 가정하지 않는다.

- 탐색과 형상 생성: 1.4절의 절차 1~4(윗면 높이 → 네 방향 모서리 → 윗면 사각형과 외곽 엣지·경로 후보 → 직육면체).

- 관제 모니터링 화면: React·Three.js 기반 실시간 3D 표시, 작업 시작·작업 중지·안전복귀·재시작의 독립 버튼과 명령, 단계·좌표·오류의 시간순 로그 및 재시작용 작업 기록. MQTT·FastAPI·Spring Boot·PostgreSQL을 통한 웹 연동·저장 구조를 적용한다(4.7절).

- RG2로 단단히 파지하는 무센서 탐침 팁·고정 홀더 제작, 로봇 내장 힘 감지(robot_force)와 가상 접촉(sim) 구현을 포함한다. RG2 쐐기·폭 변화 방식은 구현 및 실험 범위에서 제외한다.

- MVP 합격 목표: 모서리 좌표와 윗면 높이 오차 ±3 mm 이내. 오차를 1 mm 수준(±1 mm 이내)까지 줄이는 것은 MVP 이후 목표이다.

## **제외 범위 (Out of Scope)**

- 실제 용접 이음의 식별·검증, 용접 토치 자세 및 공정 조건을 반영한 실행 경로 검증, 실제 아크 용접, 용접기 연동, 열변형 보정, 비전 센서, RG2 쐐기·폭 변화 방식의 구현·실험.

## **4.5 안전 (Safety)**

| **번호** | **요구사항 설명** | **우선순위** |
| --- | --- | --- |
| 4.5.1 | 작업 중지 요청 시 이동 정지와 순응·힘 제어 해제를 수행하고 중단 위치·진행 기록을 남겨야 한다. 요청 접수와 실제 정지 완료를 구분하여 로봇 상태로 확인한다. 작업 중지는 홈 안전복귀·재시작을 자동 실행하지 않는다. | Must |
| 4.5.2 | 순응·힘 제어는 예외가 발생해도 반드시 해제되어야 한다(finally 보장). | Must |
| 4.5.3 | 과대 외력(설계 출발값 30 N)을 감지하면 메인 PC에서 즉시 작업 중지를 요청하고 원인·위치·단계를 기록해야 한다. safety_monitor는 웹 경유 없이 robot_manager에 정지를 요청한다. 홈 안전복귀는 별도 명령이며 이상 상태별 허용 조건은 환경 세팅 후 확정한다. | Must |
| 4.5.4 | 모서리에서 팁이 떨어질 때의 하강량을 제한(기본 5 mm)해 팁과 부재 옆면의 충돌을 막아야 한다. | Must |

※ 화면의 작업 중지 버튼은 소프트웨어 정지 명령이며 안전 등급 기능이 아니다. 최종 안전 수단은 티치펜던트의 물리 비상정지 스위치와 협동로봇의 충돌 감지이고, 본 시스템은 이 설정을 변경하지 않는다. 작업 중지, 홈 안전복귀, 재시작은 각각 독립 명령으로 실행한다.

## **4.7 시스템 구성과 인터페이스**

아키텍처 v1.3과 설계 요약 [E20]을 반영한 구성이다. 자체 ROS 2 실행 노드는 아래 5개이며, geometry_estimator는 scan_manager 내부 모듈이다. 기존 hmi_node의 역할은 웹 화면과 mqtt_bridge로 재배치한다. 제공 드라이버·DB·브로커와 내부 모듈은 자체 노드 수에 포함하지 않는다.

| **배치** | **구성** | **책임과 상태** |
| --- | --- | --- |
| **메인 PC** | ROS 2 Jazzy 자체 노드 5개 | scan_manager·robot_manager·contact_detector·safety_monitor·mqtt_bridge. 로봇 제어·판정·로컬 감시·계산·원본 보관. |
| **웹 PC** | Mosquitto / FastAPI / Spring Boot / PostgreSQL | 단일 MQTT 브로커, 실시간 명령·WebSocket·측정 쓰기, 업무 관리·이력 조회, 영구 DB 저장. |
| **브라우저** | React + Three.js | 독립된 네 조작 버튼, 단계·로그·TCP·측정점·외곽 엣지·경로 후보·형상 표시. |
| **로봇 측** | M0609 / RG2 / 두산·RG2 제공 드라이버 | 실제 동작·상태 제공·탐침 파지. dsr_controller2·onrobot_driver 등 실제 실행명과 버전은 환경 기록으로 대조한다. |

- 명령 흐름: 브라우저 → FastAPI → 웹 PC의 MQTT 브로커 → mqtt_bridge → scan_manager → robot_manager. 데이터는 메인 PC에서 mqtt_bridge·MQTT·FastAPI를 거쳐 화면과 DB로 전달한다. Spring Boot는 업무 데이터 쓰기와 측정 이력 조회를 담당하며 로봇 모션을 직접 제어하지 않는다.

- 내부 구성: geometry_estimator는 scan_manager 내부 계산 모듈, result_store는 로컬 보관 모듈, contact_scan_interfaces는 메시지·서비스·액션 정의 패키지이다. 이 구성요소들은 자체 실행 노드 수에 추가하지 않는다.

인터페이스 표의 경로·타입은 아키텍처의 초안 표기이며 확정 계약이 아니다. 이름·필드·오류 코드·QoS·단위·프레임을 확정할 때 구성도·문서·구현을 함께 갱신한다. 재시작은 기존 필수 요구사항으로 유지하되 전용 연결 방식과 이름은 TBD이다. 자동 캘리브레이션 경로는 MVP 필수 인터페이스에 포함하지 않고 환경 세팅 후 범위를 검토한다.

- 데이터 계약: TCP·힘을 한 샘플로 묶어도 각 취득 시각을 보존한다. 판정 좌표와 정지 완료 좌표를 구분하고, 프레임·단위 변환은 robot_manager에서 관리한다. ROS 내부 m·rad·N·N·m, 웹 길이 mm는 제안이며 최종 계약에서 확정한다. 50 Hz 수집·10 Hz 표시·1 Hz heartbeat 역시 설계 목표이지 측정 결과가 아니다.

- 명령·저장 계약: 명령 ID로 중복 실행을 방지하고 접수 응답과 동작 완료를 구분한다. 명령 retain=false는 설계 방향이며 QoS·재전송·만료 정책은 계약에서 확정한다. MQTT 전달 확인을 PostgreSQL 커밋 완료로 간주하지 않는다. FastAPI는 측정·이벤트·기준값 이력의 DB 쓰기, Spring Boot는 업무 데이터 쓰기와 측정 이력 조회를 담당한다. 기준값 이력 저장이 자동 캘리브레이션 채택을 뜻하지 않는다.

# **5. 비기능 요구사항 (Non-Functional Requirements)**

- **정확도·성능:** MVP 합격 목표는 모서리 좌표와 윗면 높이 오차 ±3 mm 이내(오차 절댓값 3 mm 이하)이다. ±1 mm 이내로 개선하는 것은 MVP 이후 목표이다. 전체 탐색 120초 이내, 관제 화면 반영 지연 200 ms 이내는 기존 목표를 유지한다(측정 방법은 9장).

- **신뢰성·안전성:** 20회 연속 탐색에서 접촉 오검출 1회 이하. 작업 중지 버튼을 누른 뒤 1초 이내에 정지하고, 모든 종료 경로에서 순응·힘 제어를 해제한다. 중단 전 확정 측정값과 작업 진행 기록은 재시작에 사용할 수 있도록 보존한다.

- **이식성·시험 용이성:** 용접기 모델·와이어 상태·표면 통전 여부에 의존하지 않는다. 접촉 감지는 로봇 내장 힘 감지만으로 동작하고, sim 입력원으로 Virtual Mode에서 전체 흐름과 관제 화면을 실행할 수 있어야 한다.

# **6. 종속성, 가정 및 제약조건**

## **종속성 (Dependencies)**

- 실기 로봇(M0609 + RG2) 사용 시간 — 실제 접촉은 실기에서만 검증할 수 있다 [E10].

- 무센서 탐침 팁과 RG2 핑거에 유격 없이 맞물리는 고정 홀더의 제작(3D 프린트), RG2 + 탐침의 툴 무게·무게중심·TCP 등록. 물품 도착 및 환경 세팅 완료 후 실제 좌표 기준을 확정한다.

- 치수를 버니어 캘리퍼스로 잰 기준 직육면체(2종 이상 권장)와, 원점·축 방향이 표시된 배치 가이드.

## **MVP의 배치 가정과 그 한계 (솔직한 기재)**

- **원점 정렬:** MVP에서는 사람이 배치 기준에 맞춰 부재를 놓는다. 기준의 실제 위치와 좌표값은 환경 세팅 후 확정한다. 축 평행이고 탐색 기준점이 윗면 위에 있으면 중심이 어긋나도 모서리 좌표는 측정할 수 있다(1.4절).

- **축 평행:** 가장 강한 가정이다. 2° 회전에 꼭짓점이 축당 약 1.7 mm 어긋난다(100 mm 변). 직각 스토퍼로 억제하며, 이 가정의 제거가 MVP 이후 첫 과제이다.

- **직육면체 한정:** 윗면은 수평, 옆면은 수직, 모서리는 날카롭다고 본다. 모따기·라운드는 소실 위치를 바깥으로 밀어 편향을 만든다.

- **‘티칭 제거’의 범위:** MVP가 없애는 것은 좌표 교시이며, 배치 규칙과 형상 종류라는 사전 정보는 남는다. MVP는 “치수를 모르는 부재의 외곽 엣지·경로 후보 좌표를 만져서 얻는다”는 핵심 원리를 실증한다.

- **결과물의 정의: MVP 출력은 단일 직육면체의 윗면 외곽 엣지 4개와 이를 기반으로 한 경로 후보이다. 외곽 엣지라는 기하학적 사실과 실제 용접 이음이라는 공정 의미를 구분한다. 바닥면 등 다른 모서리를 선택하더라도 실제 이음의 존재·용접 가능성·접근 자세가 자동 검증되는 것은 아니다.**

## **제약조건 (Constraints)**

- M0609 가반하중 6 kg, 최대 반경 900 mm [E4]. 부재와 탐색 경로가 작업 영역 안에 있어야 한다.

- RG2는 힘 측정값을 제공하지 않으므로 [E17][E18] 접촉은 로봇 내장 힘 감지로 판정한다. Virtual Mode에서는 순응/힘 제어가 정상 동작하지 않을 수 있다 [E10].

- API 계층과 버전의 차이: DRL 매뉴얼 [E10], 저장소의 ROS2 Python 래퍼·서비스 정의 [E18], 팀의 실제 PC 확인 [E19]을 구분한다. stop()·set_external_force_reset()의 Python 노출 여부와 대체 호출 경로는 사용 중인 패키지 버전 및 항목별 확인 로그와 함께 관리한다.

- 실행환경과 연동: 아키텍처는 메인 PC Ubuntu 24.04·ROS 2 Jazzy와 웹 PC 분리를 전제로 한다. DART 2.12.1·DRCF 및 두산 드라이버의 실제 버전·지원 기능·호환 여부는 항목별 PC 확인 기록으로 확정한다. 웹 PC의 Mosquitto·FastAPI·Spring Boot·PostgreSQL 연결 및 시간 기준 설정이 관제 지연 측정의 선행조건이다.

- 교과 프로젝트 기간과 공유 장비 일정, 추가 센서 예산 0원(탐침 출력비 제외).

## 환경 세팅 후 확정할 항목

- 좌표 기준: 환경 세팅 후 작업대 원점·축 방향, 실제 물체 지지면과 z=0 기준, 로봇 Base 변환, 탐침 TCP 기준점·자세·오프셋을 확정한다. 물체가 지그 위에 놓이면 지그 지지면과 작업대 표면을 구분한다. 높이 계산·하단 투영은 확정한 지지면 기준을 적용한다. base_link·workpiece_fixture 등 프레임명은 가칭이다.

- 자동 캘리브레이션: 기준면을 자동 접촉 측정하여 보정·저장·재사용하는 절차는 아키텍처의 검토안이다. 현재 MVP의 필수 기능이나 시작 전 필수 Action으로 확정하지 않는다. 환경 세팅 후 좌표계·기준과 설정 방법을 정하고 자동화 적용 여부·범위를 검토한다. 기존 무접촉 힘 영점 요구사항(4.1.3)은 별개로 유지한다.

- 홈위치: 안전복귀 목적지는 홈위치(시작위치)로 확정하였다. 실제 홈 자세와 좌표값은 환경 세팅 후 확정한다. 방향별 정상 탐색 사이의 원점 복귀와 관제자의 홈 안전복귀 명령은 구분한다.

- 미결정 사항: 홈 복귀 경로·순서, 중단 위치 재접근 절차, 이상 상태별 재시작 허용 조건, 정지 우선순위·래치 해제 조건, 데이터 최신성·허용 시각 차이, heartbeat 만료·브라우저 단절 정책, 재접속 후 재전송·저장 확인 절차는 상세 설계에서 확정한다. 구체적인 경로·높이·속도·시간·허용 조건은 팀 확인 없이 정하지 않는다.

- 실기 검증 선행조건: 좌표계·TCP·홈위치와 위 동작 조건을 확정한 후 정확도, 안전복귀 및 재시작 수락 시험을 실시한다. 미정 항목은 실기 시험 완료로 간주하지 않는다.

| **“이미 있는 기술 아닌가?”** | 접촉으로 이음을 찾는 와이어 터치센싱은 상용 기술이다 [E5][E8]. 비전으로 스캔해 경로를 자동 생성하는 제품도 있다 [E14]. | 터치센싱은 이미 교시된 경로를 예상 위치와 비교해 오프셋할 뿐이며 [E7][E9], 두산의 용접 API도 Y·Z 오프셋 보정 구조이다 [E10]. 즉 티칭이 먼저 있어야 한다. 비전 방식은 티칭을 없애지만 센서를 더해야 한다. **“센서 추가 없음”과 “티칭 없음”을 동시에 만족하는 조합**이 우리의 자리이다. |
| **“촉각 탐색은 느리지 않은가?”** | 느리다. 와이어 터치센싱은 조인트당 3~5초, 2D 카메라는 0.1초 단위이다 [E5]. 우리 MVP는 5점에 약 2분을 목표로 한다. | 비교 대상은 비전이 아니라 **사람의 재티칭(15~30분 이상 [E13])**이다. 탐색은 품종 교체 시 한 번이고 그동안 사람이 필요 없다. 2단 속도와 탐색 순서 최적화로 60초까지 줄이는 것이 다음 목표이다. |
| **“그리퍼 힘 피드백 감도로 접촉을 안정적으로 잡을 수 있는가?”** | RG2 제품·소스 설명에 힘 측정 피드백은 없다 [E17][E18]. 쐐기·폭 변화 개념은 가정값에 따른 계산만 검토하였다. 실험하지 않았으므로 감도 부족이나 자기잠김이 실제로 발생한다고 단정하지 않는다. | RG2는 고정 탐침 파지에 사용하고 M0609의 외력 추정과 TCP 위치 변화로 접촉·엣지를 판단하도록 설계한다. B의 3 N 접촉 검출 성능은 아직 실기 검증하지 않았다. A는 향후 실험 계획도 없으며 프로젝트 범위에서 제외한다. |
| **“비전 대비 장점은?”** | 속도, 곡면, 복잡 형상, 임의 배치에서는 비전이 우위이다. | 반사 표면·아크광·스패터·연기에서 레이저 비전은 실패하기 쉽고 [E11], 가격은 1만~5만 달러 이상이다 [E12]. 촉각은 먼지·오염으로 시야가 막힌 곳에서 유용하며 [E12], 센서 구매와 핸드아이 캘리브레이션이 없다. 장기적으로는 경쟁이 아니라 보완 관계이다. |
| **“부재를 원점에 맞춰 놓는 것도 결국 티칭 아닌가?”** | MVP에서는 그렇게 볼 수 있다. 위치와 방향을 사람이 맞춘다. | 사람이 하는 일은 좌표 입력이 아니라 스토퍼에 밀어 넣는 것이며, 치수는 로봇이 스스로 잰다. 중심 오차에는 원리적으로 둔감하고(1.4절), 회전 가정은 MVP 이후 변마다 2점 탐색으로 제거한다. |

※ 차별점 1의 정확한 표현: 와이어 터치센싱도 로봇에 별도 센서를 달지는 않는다 [E7]. 다만 감지 기능을 갖춘 용접 전원과 와이어 커터·브레이크에 의존하고 [E6][E7], 통전되는 깨끗한 표면이 필요하다 [E8]. 우리의 주장은 “용접기와 표면 상태에 의존하지 않고, 셀에 이미 있는 로봇의 힘 감지와 그리퍼만 쓴다”이다.

**수락 기준 (Acceptance Criteria)**

- 좌표를 한 점도 교시하지 않은 상태에서 직육면체의 외곽 엣지·경로 후보 4개와 형상이 위 오차 기준 안에서 생성된다.

- 치수가 다른 직육면체로 바꾼 뒤 코드나 좌표 수정 없이 다시 실행해도 같은 기준을 만족한다.

- 탐색의 모든 단계가 관제 화면의 3D 뷰와 로그에 실시간으로 나타난다. 작업 시작·작업 중지·안전복귀·재시작 버튼은 별개 명령으로 동작한다. 작업 중지·미접촉·과대 외력·예외 시 이동이 중단되고 순응·힘 제어가 해제되며 원인과 진행 기록이 로그에 남는다.

- 작업 중지만 요청하면 중단 상태를 유지하며 자동으로 홈 복귀하거나 처음부터 다시 탐색하지 않는다. 안전복귀 버튼을 별도로 누르면 홈위치(시작위치)로 복귀한다.

- 관제자가 재시작 버튼을 누르면 작업 로그에서 중단 단계·탐색 방향·중단 위치와 기존 측정값을 확인하고, 기존 측정값을 유지한 채 중단 위치부터 탐색을 이어간다. 예를 들어 +x 탐색 중 중단했다면 이미 얻은 윗면 높이를 유지하고 +x 탐색을 이어간다.

- 재시작 전후의 작업 기록으로 기존 측정값 유지와 중단 구간의 연속 실행을 확인한다. 안전복귀를 거친 재시작의 구체적인 재접근 경로·순서 및 이상 상태별 허용 조건은 6장의 미결정 사항 확정 후 검증한다.

# **10. 요구사항 정의서 (BR / TR)**

시스템·기능 요구사항(SR·FR)은 4장, 비기능(NFR)은 5장, 인터페이스 설계는 4.7절에 정의한다. 본 장은 비즈니스 요구사항과 시험 요구사항을 정리하며, 시험 항목 기재는 시험 수행 완료를 뜻하지 않는다.

삭제 이력: RG2 쐐기 실험 요구사항 4.1.7과 TR-06은 철회하여 번호를 재사용하지 않는다. 위험 8도 실험 계획 철회에 따라 삭제하였다.

# **12. 작성 시 가정 사항 및 변경 이력**

[v3.0.0 변경] 팀 회의 및 후속 확인을 반영하였다. MVP 합격 목표를 ±3 mm로 확정하고 ±1 mm는 MVP 이후 목표로 옮겼다. 작업대·Base·TCP의 실제 기준은 물품 도착 및 환경 세팅 후 확정하는 항목으로 명시하였다.

[v3.0.0 변경] 작업 중지·안전복귀·재시작의 기능·버튼·명령을 분리하였다. 안전복귀 목적지는 홈위치(시작위치)이다. 재시작은 관제자 명령으로 로그를 확인해 기존 측정값을 유지하고 중단 위치부터 이어간다. 관련 사용자 스토리, 기능 요구사항, 인터페이스, 노드 구성도, KPI와 시험 항목을 함께 수정하였다.

[개정 범위] B안 문서와의 결합은 v3.1.0에서 검토하며 이번에는 수행하지 않는다. 접촉 감지 방식 B(robot_force)는 기존 기술 선택으로 별도 BRD인 B안 문서와 구분한다. 새 아키텍처의 구조·역할을 반영하되 정확도·필수 출력·좌표 기준은 최신 팀 합의를 우선한다. 경제성 가정·반복성 등 변경 합의가 없는 기존 지표는 유지한다.

- **[v2.1 이력 정정] 로봇 내장 힘 감지(B)를 기본으로 선택한 결정은 유지한다. 이전 문서의 RG2 쐐기 방식 비교 실험 계획은 철회하였다. 해당 방식은 실험한 적이 없으며 구현·실험 요구사항 4.1.7과 TR-06은 삭제하였다. 이론 검토 결과를 실측 결과나 실패가 입증된 사실로 해석하지 않는다.**

- **[v3.0.0 후속 정정] 쐐기 검토는 대칭 쐐기 모형·가정 마찰계수·가정 하중에 따른 조건부 계산이다(1.4절). 실험 근거가 아니며 실제 역구동·자기잠김·폭 변화 발생 여부는 확인되지 않았다. 기존 “팀이 3 N 접촉 판정을 구현해 보았다”는 문구는 삭제하였다. API 매뉴얼 설명, 저장소 소스 확인, 팀의 실제 PC 확인, 실기 접촉 성능 검증은 각각 구분한다.**

- [v3.0.0 출력 정정] MVP 결과는 외곽 엣지·경로 후보이며 윗면의 네 변 출력은 Must로 유지한다. 실제 용접에 대한 장기 비전과 상용 기술·참고문헌의 용접선 용어는 의미를 유지한다. 아키텍처의 ±5 mm·도전 ±3 mm 수치는 채택하지 않고 MVP ±3 mm·이후 ±1 mm를 적용한다.

- **근거 자료·적용 로봇: 외부 자료 [E1]~[E18]은 기존 문서의 조사 근거, [E19]는 팀의 후속 사실 확인, [E20]은 최신 아키텍처와 적용 범위 확인이다. 적용 로봇은 M0609이며 RG2에 무센서 탐침을 파지한다. 설계 반영은 코드 구현·실로봇 성능 검증 완료를 의미하지 않는다.**

- **차별점 표현의 조정:** “센서를 추가로 달지 않는다”는 와이어 터치센싱에도 해당하므로 [E7], “용접기·표면 상태에 의존하지 않고 셀에 이미 있는 것만 쓴다”로 정밀화하였다. 비전 기반으로 티칭을 없앤 제품이 있으므로 [E14] 고유성은 “무티칭 + 무센서”의 조합으로 한정하였다.

- **[v3.0.0 아키텍처 반영] 자체 노드는 scan_manager·robot_manager·contact_detector·safety_monitor·mqtt_bridge의 5개이다. geometry_estimator는 scan_manager 내부, result_store는 로컬 보관 모듈, contact_scan_interfaces는 인터페이스 정의 패키지로 구분한다. 기존 노드 그림은 4.6~4.7절의 역할·배치·연결 표로 대체하였다. 인터페이스 이름·타입은 초안이며 미정 항목을 확정 사실로 취급하지 않는다.**

- **[v3.0.0 웹 연동 변경] 기존 rosbridge·roslibjs 중심 관제안을 MQTT·FastAPI·Spring Boot·PostgreSQL·React·Three.js 구조로 갱신하였다. 정지·접촉 판정은 메인 PC에서 처리하고, 웹은 명령·표시·저장·업무 이력을 담당한다. 자동 캘리브레이션은 MVP 필수로 추가하지 않으며 좌표계·기준은 환경 세팅 후 확정한다.**

- **수치의 성격:** 경제성 [A1]~[A9]는 [A3] 보수값을 제외하고 모두 가정이며 최종 비전 기준이다. [E13]이 시사하는 불리한 경우는 보수적 시나리오와 위험 9에 반영하였다. 접촉 임계 3~5 N, z 급강하 판정 0.5 mm, 누름 힘, 팁 반지름 3 mm, 판정 지연 40 ms, 하강 제한 5 mm, 과대 외력 30 N은 설계 출발값이며 실측으로 조정한다. 와이어 터치센싱 옵션과 오프라인 프로그래밍 SW의 가격은 근거를 확보하지 못해 “미확인”으로 두었다.
