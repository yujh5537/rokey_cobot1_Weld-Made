# robot_manager · 좌표 · TCP 정리 (1차 스캔, 2026-09-18 ~ 09-23)

담당: 학민 · 관련 이슈: #109 · #113 · #123 · #125 · #130 · #137 · #147 · #152 · #153 · #155 · #159 · #167 · #180 · #186 ·
관련 PR: #127 · #135 · #138 · #156 · #160 · #168 · #169 · #174 · #181 · #188

## 1. 맡은 것과 범위

두산 M0609 + RG2 를 부르는 **유일한 노드**(`robot_manager`)와, 그 노드가 쓰는 **좌표 기준**(TCP · 홈 ·
작업대 원점 · z=0, `docs/contracts/units-frames.md`)을 맡았다.

- **만든 것**: `/robot/sample`(50 Hz 시도) · `/robot/status` 발행, `/robot/execute_motion` Action 4 동작
  (MOVE_TO · DESCEND · SLIDE · HOME), `/robot/stop` 서비스, 두산 호출 직렬화(`CallQueue`),
  **SLIDE 스텝 모드**(`step_slide.py`), 단위 · 프레임 변환.
- **안 한 것**: 접촉 판정 자체(contact_detector, 현지), 탐색 순서(scan_manager, 병후), 안전 감시(safety_monitor, 현지).
  robot_manager 는 **판정하지 않고 실행하고 멈춘다.** 접촉 · 모서리는 `/contact/event` 로 받는다 —
  단, 스텝 모드에서는 EDGE 를 robot_manager 가 확정한다(아래 2 절).

## 2. 설계 — 핵심 결정 셋

### 2.1 두산 호출을 한 줄로 세운다 (`call_queue.py`)

`get_current_posx` 와 `get_tool_force` 를 동시에 부르자 `dsr_controller2` 가 **모든 서비스 응답을 멈췄고**
브링업을 다시 띄워야 회복됐다(2026-09-20 Virtual, `docs/env/api-check-log.md`).
→ 조회 · 모션 · 정지를 전부 한 줄(`CallQueue`)에 넣고, `call_async` + 콜백만 쓴다.

- 대안: 조회만 직렬화하고 모션은 따로 — 모션 호출도 같은 드라이버를 쓰므로 같은 위험이 남는다. 버렸다.
- 대가: 호출이 잦아지면 큐가 밀리고 샘플 공백이 길어진다(5.5 절, #130).

### 2.2 SLIDE 를 힘 제어에서 **스텝 모드**로 바꿨다 (`step_slide.py`, 계약 v0.1.15, PR #160)

연속 힘 제어 SLIDE 는 **움직이는 중의 외력 추정값이 방향마다 1.5~8.6 N 치우쳐**(2026-09-22 T25) 누름을
믿을 수 없었고, 방향 전환 뒤에는 힘 제어가 누름을 더해 주지 못해 2~4 방향이 떠서 모서리를 놓쳤다(#155).
→ 위치 제어로 한 스텝 가고, **멈춘 뒤 새로 받은 샘플만 평균낸 ΔFz** 로 판정한다.

- 근거는 9/17 프로토타입(`tactile_probe/edge_scan.py`)이 같은 M0609 로 원점 + ±X · ±Y 를 한 번에 끝낸 것이다.
- 대안: 힘 제어를 유지하고 방향 전환 때만 재하강(`OP_DESCEND`) 추가 — 계약 7.3 변경이 필요하고
  스텝 모드가 스스로 `step_press_max_m`(3 mm)까지 눌러 같은 문제를 덮는다. #155 에 남겼다.
- 대가: **느리다.** 한 방향 50~70 s, 전체 탐색의 76 %(4.3 절, #180).
- 이 결정으로 **EDGE 확정이 contact_detector 에서 robot_manager 로 옮겨 왔다**(계약 v0.1.15).

### 2.3 "멈춘 것"과 "도착한 것"을 나눈다 (PR #156 · #174)

두산 서비스의 `success` 는 **"명령을 받았다"이지 "그 자세가 됐다"가 아니다.** 도달 불가 자세에
`move_line` 을 보내면 로봇이 한 번도 움직이지 않은 채 `success=true` 가 8 회 연속 온다(2026-09-23, #186 M1).
→ 도착은 **위치로** 확인한다. 멈췄는데 목표에서 `arrival_tolerance_m`(3 mm) 밖이면 `ROBOT_ERROR(204)` 다.
명령 뒤 `arrival_grace_s`(1 s) 안에 출발하지 않으면 `move_stop` 뒤 한 번 다시 보낸다.

## 3. 구현

```
                    ┌──────────────── robot_manager ────────────────┐
  /contact/event ──▶│ on_event  (motion_id · operation 대조)         │
  /robot/stop    ──▶│ 접수만 — 정지 확인될 때까지 남는다             │
                    │                                               │
  /robot/execute_motion ─▶ Action 서버                              │
                    │   ├ MOVE_TO / DESCEND / HOME → watch 루프      │
                    │   └ SLIDE ─┬ force : 순응+힘 제어 후 watch     │
                    │            └ step  : step_slide.run(StepIO)    │
                    │                                               │
                    │  ┌─ 샘플 타이머 50 Hz ─┐                       │
                    │  │ posx → force →      │                       │
                    │  │ (5 회에 1 번) state │                       │
                    │  └──────────┬──────────┘                       │
                    │       CallQueue  ← 두산 호출은 전부 여기 한 줄  │
                    └────────────┬──────────────────────────────────┘
                                 ▼  dsr_controller2 (dsr01)
                    /robot/sample (BEST_EFFORT) · /robot/status
```

**스텝 모드 한 방향의 절차** (`step_slide.py`, 로봇을 부르는 일은 `StepIO` 뒤에 둬 rclpy 없이 시험한다)

0. **기준 힘** — `step_lift_m` 들고 긁을 방향으로 `step_nudge_m` 움직여 멈춘 뒤 F0 를 잰다.
   마지막 이동 방향을 긁기와 같게 두는 이유: 멈춘 상태에서도 마지막 이동 방향만으로 Fz 가 1.9 N 달라진다(9/21 실기 1-1).
1. **누르기** — `step_press_step_m`(0.1 mm)씩 내려가 ΔFz ≥ `step_release_n`(2.5 N)이면 닿음.
2. **긁기** — `step_coarse_m`(0.5 mm) 이동 → ΔFz 를 [3, 7] N 으로 유지하도록 z 를 `step_z_m`(0.05 mm)씩 조절.
   힘이 빠지면 최근 접촉 높이(중앙값)보다 `step_drop_m`(0.5 mm) 아래까지 내려가 보고, **그래도 3 N 미만일 때만** 소실 후보.
3. **다듬기** — 마지막으로 제대로 누른 자리보다 한 스텝 뒤에서 공중 F0 를 다시 재고 `step_fine_m`(0.1 mm)씩 전진.
4. **마무리** — `step_lift_m` 만큼 든다(팁을 모서리에 걸쳐 두지 않는다).

**소실 기준을 `release_n`(2.5 N)이 아니라 `follow_lo_n`(3 N)으로 둔 이유**: 모서리를 넘으면 반지름 약 2 mm 팁이
모서리 각에 걸려 1~2 N 이 남는데, 이 값이 F0 치우침(±0.6 N)만큼 `release_n` 을 넘나든다.

## 5. 문제와 해결

### 5.1 힘 제어 SLIDE 가 실기에서 누르지 못했다 (9/22)

- **증상**: 방향 전환 뒤 출발한 2~4 번째 방향이 약하게 닿거나 떠서 모서리를 놓쳤다. `20260922-135809` 는 −x 가
  허공 밀기로 `NO_EDGE(301)`, `20260922-141020` 은 힘 제어를 켜는 순간 0.15 mm 들려 누름이 1 N 아래로 떨어졌다.
- **원인**: 움직이는 중의 외력 추정값이 방향마다 **1.5~8.6 N** 치우친다. 목표 힘을 6 → 10 N 으로 올려도
  밀기 중 누름은 바뀌지 않았다 — **출발 시점의 누름이 밀기 내내의 접촉을 정한다.**
- **조치**: 위치 제어로 한 스텝씩 가고 멈춰서 힘을 읽는 **스텝 모드**를 넣었다 (PR #160, 계약 v0.1.15).
- **결과**: 9/22 스텝 모드 실기 3 세션에서 **모서리 14/14 검출**, 허공 밀기 0 회.
- **교훈**: 움직이는 중의 외력 추정값은 판정 기준으로 쓸 수 없다. **멈춰서 읽으면 쓸 수 있다.**

### 5.2 멈춘 것을 도착으로 읽었다 — 가짜 도착 4 가지 (9/23)

- **증상**: 로봇이 목표에 가지 못했는데 `TARGET_REACHED` 로 끝났다. 1 mm/s 하강은 아예 "이동"으로 읽히지 않아
  출발 직후 도착 판정이 났다(3/3 재현).
- **원인**: 도착을 두산 `success` 와 "지금 안 움직인다"로만 판정했다. `moving_eps_m`/`moving_window_s` 가
  지켜 주는 최저 속도가 0.2 mm / 0.3 s ≈ **0.67 mm/s** 라 그보다 느린 이동은 정지로 보인다.
- **조치**: 도착을 **위치로** 확인한다(`arrival_tolerance_m` 3 mm). 출발하지 않으면 `move_stop` 뒤 한 번
  다시 보낸다(`arrival_grace_s` 1 s, `move_restart_max` 1). (PR #156 · #174)
- **결과**: 9/23 종단 3 회 연속 성공. 가짜 도착 0 회.
- **교훈**: 드라이버의 성공 응답은 명령 접수의 증거이지 상태의 증거가 아니다.

### 5.3 두산 `success` 는 어느 방향으로도 못 믿는다 (9/23 M1)

- **증상**: 45° 용접 자세 도달성 점검에서 L1 이 `reach=1` 로 기록됐다. 실제로는 **한 번도 움직이지 않았다.**
- **원인**: 점검 스크립트가 `move_line` 의 `success` 만 봤다. 증거는 L1 start 와 end 의 실측 posx 가
  `[460.88, −201.17, 209.89]` 로 **완전히 같다는 것**이다 — 앞 자세를 마치고 30 mm 올린 자리다.
  `move_jointx` 도 같고, `motion/ikin` 은 sol 0~7 전부 `success=true` 에 J2 = 29914° 같은 값을 준다.
- **조치**: 실측 posx 와 지령을 **1 mm 로 비교**하도록 고쳤다(`ARRIVE_TOL_MM`). 자세(ZYZ)는
  `(A, B, C) ≡ (A+180, −B, C+180)` 두 표현으로 와서 비교에서 뺐다. (#186)
- **결과**: 16 자세 중 **12 도달 · 4 불가**로 다시 판정됐고, 도달 12 자세의 위치 오차는 최대 0.14 mm 였다.
- **교훈**: 5.2 와 같은 실수를 도구에서 다시 했다. **판정 기준은 코드마다 따로 세우지 말고 한 곳에서 빌려 와야 한다.**

### 5.4 탐침 교체와 작업대 재설치로 좌표 기준을 전부 잃었다 (9/21~23)

- **증상**: 탐침이 홀더 안으로 밀려 80 분 사이 0.6 → 1.3 mm 짧아졌고, 그 세션의 z 값이 전부 무효가 됐다.
  이어 작업대를 교체해 z=0 과 TCP z 를 **동시에** 잃었다.
- **원인**: 기존 교체 절차(옛 TCP 로 등록한 채 아는 z=0 을 접촉해 차이로 새 TCP z 를 구함)는 **z=0 을 알 때만**
  쓸 수 있다. 자유도가 둘인데 식이 하나였다.
- **조치**: 순서를 바꿔 자유도를 하나씩 닫았다 — ① 캘리퍼로 TCP z 잠정 등록 → ② 지지면 접촉으로 z=0 확정 →
  ③ 큐브 윗면 접촉 높이를 캘리퍼 80 mm 와 검산 → ④ J6 180° 로 TCP x · y 확인 → ⑤ 팁 반지름 → ⑥ 툴 재등록.
  (#147 · #137 → PR #138 · #169)
- **결과**: TCP `[0, 0, 252.12]`, z=0 = 95.006 mm 로 다시 세웠고 9/23 종단이 3 회 연속 성공했다.
- **교훈**: **독립적으로 아는 값(캘리퍼 80 mm)이 하나 있으면 미지수 둘을 풀 수 있다.** 그 값을 먼저 찾는다.

### 5.5 정지 중 3 s 주기 샘플 공백이 스캔을 멈췄다 (9/21)

- **증상**: 로봇이 서 있는 동안 `/robot/sample` 이 3 s 주기로 300~360 ms 끊겼고, goal 시작과 겹치면
  safety_monitor 가 `SAMPLE_STALE(403)` 로 정지시켰다. 한 세션에 4 회, 약 6 분에 goal 5 개가 죽은 회차도 있다.
- **원인**: **찾지 못했다.** robot_manager 에는 3 s 주기 작업이 없다는 것까지만 확인했다(타이머는 샘플 50 Hz ·
  상태 10 Hz 둘뿐). 드라이버 · DRCF 쪽 주기 작업으로 추정한다.
- **조치**: ① 늦은 호출을 이름 · 시간과 함께 기록(`slow_call_warn_s`, PR #135) ② `sample_stale_ms` 300 → **500**
  (PR #168) ③ 시연 중 발생 시 대응표(`daily/20260923.md` §7).
- **결과**: 9/23 종단 3 회에서 중단 없음. 다만 9/22 기록에 **500 ms 를 넘는 공백이 2 건**(699 · 748 ms) 있어
  완전히 막히지는 않았다. #130 은 열려 있다.
- **교훈**: 원인을 못 찾은 것은 **못 찾았다고 적고** 완화책과 남은 위험을 같이 남긴다.
