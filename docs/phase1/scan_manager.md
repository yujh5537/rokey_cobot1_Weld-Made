## 5. 문제와 해결

### 5.1 감시자가 죽었는데 스캔은 계속 시작됐다 — 상태 토픽의 나이로 START · RESUME 을 막았다 (9/21 실기)
- **증상**: 2026-09-21 실기에서 safety_monitor 가 10:34:33 · 11:51:45 에 두 번 죽었다(#103. 로거 심각도 전환 결함, 현지 PR #117 로 수정). 두 번째 뒤로 **하강 5 회 · 밀기 2 회가 2차 감시 없이 돌았고, 한 시간 넘게 아무도 알아채지 못했다**(#103 · #120 본문, `docs/test-reports/realrobot-session_20260921.md` "safety_monitor 가 죽었다" 단락). 그동안 scan_manager 는 START 를 정상으로 받았다.
- **원인**: scan_manager 는 `/safety/status` 를 "**한 번도 못 받음**"일 때만 거절하고 "**받다가 끊김**"은 거르지 않았다. 이미 받은 마지막 메시지는 발행이 끊겨도 남아 있어서, 죽기 직전의 `latched=false` 가 그 뒤로 계속 "안전 정상"으로 읽혔다. 감시자가 죽은 것보다 **죽은 것을 시스템이 모르는 것**이 문제였다.
- **조치** (PR #136, 2026-09-21 머지):
  - `START` · `RESUME` 때 두 상태 토픽의 **`stamp` 나이**를 한도와 비교한다. `/safety/status` 가 끊겼으면 `SAFETY_LATCHED(103)`, `/robot/status` 가 끊겼으면 `ROBOT_DISCONNECTED(104)`로 거절하고, detail 에 "끊김(마지막 stamp 가 N.N s 전, 한계 N.N s)"을 적는다. "미수신"과 "끊김"은 같은 코드에 다른 detail 이다(0 · false 로 적지 않는다).
  - 한도는 파라미터다: `safety_status_timeout_s` 5.0 · `robot_status_timeout_s` 2.0(설계 출발값, 발행 주기의 5 배 · 20 배).
  - 끊긴 순간과 돌아온 순간을 `/scan/log` 에 한 번씩 남긴다(누르기 전에 알린다). 안전복귀(`HOME`)는 `/safety/status` 가 끊겨도 막지 않는다(규칙 3).
  - 판정은 순수 함수 `status_stale()` 이 한다. 경계(정확히 한계 시간 · 미래 stamp · 시계 0 · 한도 없음)를 ROS 없이 시험한다.
- **결과** (sim 종단, 격리 도메인 36 · PR #136 본문):
  - safety_monitor 만 죽이자 START 가 `103 /safety/status 끊김(마지막 stamp 가 5.5 s 전, 한계 5.0 s)` 로 거절됐다.
  - 거절(298.25 s)보다 **먼저** 끊김 WARN(297.87 s)이 `/scan/log` 에 떴다.
  - safety_monitor 를 다시 띄우자 "수신 회복" INFO 1 회 뒤 103 이 풀렸다.
  - 시험 1101 → **1124 개, 실패 0**, 클린 빌드 포함 5 회 실행 모두 실패 0.
- **남은 것**: **실기에서 다시 확인하지 않았다.** 이 관문은 시작 때만 본다. **진행 중인 스캔은 감시자가 죽어도 끝까지 간다**(끊김 WARN 만 남는다). 그래서 9/22 안전 감사는 "부분 해결"로 판정했다(`docs/test-reports/safety-audit-review_20260922.md` D-1). 웹의 끊김 표시도 남아 #120 이 열려 있다.
- **교훈**: 상태 메시지의 "마지막 값"은 발행자가 살아 있다는 증거가 아니다. **값과 함께 그 값의 나이를 본다.**
- 덧붙임: 이슈의 전제("TRANSIENT_LOCAL 이라 발행자가 죽어도 늦게 뜬 구독자가 마지막 값을 받는다")는 sim 종단에서 틀린 것으로 확인했다. 보관은 발행자 쪽이라 프로세스가 죽으면 늦은 구독자는 아무것도 못 받는다(PR #136 본문).
