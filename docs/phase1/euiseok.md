## 1. 맡은 것과 범위

로봇이 만든 값을 **사람이 보는 화면까지** 옮기는 길 전체를 맡았다. ROS 2 쪽 `mqtt_bridge` 노드 하나, 웹 PC 쪽 FastAPI · Spring Boot · PostgreSQL · React 3D 관제, 그리고 ROS 없이 웹을 돌리기 위한 목업 발행기다.

**하지 않은 것**: 접촉 판정 · 모션 · 안전 감시 · 형상 계산은 메인 PC 쪽(현지 · 학민 · 병후)이다. 웹은 판정을 하지 않는다. 화면의 버튼은 명령을 **보내기만** 하고, 실행 여부는 ROS 가 정한다.

## 2. 설계

### 2.1 ROS 와 웹의 접점을 문서 한 장으로 좁혔다

**결정**: 브라우저 → FastAPI → Mosquitto → mqtt_bridge → scan_manager. ROS 와 웹은 `docs/contracts/mqtt-schema.md` 한 장으로만 만난다.

**왜**: rosbridge · roslibjs 안은 브라우저가 ROS 타입을 직접 다루게 된다. 그러면 ROS 메시지가 바뀔 때마다 프런트가 깨지고, 웹 PC 에 ROS 를 깔아야 한다. MQTT 를 사이에 두면 **웹 PC 에 ROS 가 필요 없고**, 양쪽이 서로의 내부를 몰라도 된다.

**대안과 그 값**: rosbridge 는 초기 구현이 빠르다. 대신 계약이 코드에 흩어진다. 우리는 팀이 넷이고 ROS 쪽과 웹 쪽이 나뉘어 있어서, **"어디를 보면 되는지"가 한 곳인 편**이 값이 컸다.

근거: `docs/decisions/0002-web-stack-mqtt.md`, `docs/contracts/mqtt-schema.md`

### 2.2 목업 발행기로 ROS 를 기다리지 않았다

**결정**: 계약 4장의 JSON 예시를 그대로 발행하는 `backend/mock_publisher` 를 먼저 만들고, 프런트 · FastAPI 를 그것으로 개발했다.

**왜**: 9/18 에 계약을 동결했지만 `mqtt_bridge` 는 9/19 에야 담당이 정해졌다(#63). 목업이 없으면 웹은 ROS 가 돌기 전까지 아무것도 못 만든다. 실제로 T12(#56) 에서 목업과 프런트 골격을 같이 냈고, T21(#67) 브리지가 붙었을 때 **프런트를 고치지 않고** 그대로 연결됐다.

**대가**: 목업이 계약 예시와 어긋나면 그 차이가 통합 때 한꺼번에 나온다. 그래서 목업은 계약 4장 예시를 **그대로** 쓰고, 값을 지어내지 않는다.

### 2.3 쓰기와 읽기를 갈랐다

**결정**: 측정 · 이벤트는 FastAPI 가 쓰고, Spring Boot 는 **읽기만** 한다. Spring 의 Repository 를 `JpaRepository` 가 아니라 `Repository<>` 로 선언해 `save` · `delete` 가 아예 노출되지 않게 했고, `ddl-auto=none` 으로 스키마를 건드리지 못하게 했다.

**왜**: 같은 테이블에 두 서비스가 쓰면 누가 마지막에 썼는지로 싸운다. "읽기 전용"을 문서가 아니라 **타입으로** 지키면 실수할 방법이 줄어든다.

**남은 약점**: DB 계정은 아직 FastAPI 와 같다. 읽기 전용이 코드로만 지켜진다(후속).

근거: PR #134(T35), `backend/spring/README.md`

## 3. 구현

### 3.1 자료 흐름

```
로봇 ─ DRFL ─ robot_manager ─┐
                             ├─ ROS 2 토픽 ─ mqtt_bridge ─ MQTT ─ Mosquitto ─┐
scan_manager · safety_monitor ┘         (번역: m→mm, NaN→null,              │
                                          enum→이름, ROS time→epoch ms)     │
                                                                            │
브라우저 ─ Vite(5173) ─ WebSocket ─ FastAPI(8000) ────────────────────────────┤
                            └ REST /commands ─ MQTT 발행 ────────────────────┘
                                                   │
                                          PostgreSQL(5432) ─ Spring(8080) 읽기
```

그림: `docs/deliverables/assets/02-network.png`

### 3.2 mqtt_bridge — 번역기

ROS 토픽 8개를 구독해 MQTT 로 내보내고, MQTT 명령 6개를 ROS 액션 · 서비스 호출로 바꾼다. 하는 일은 **번역뿐이고 판단하지 않는다** — 단 하나의 예외가 명령 관문이다.

명령은 이 순서로 본다. 앞에서 걸리면 뒤는 보지 않는다.

```
필수 필드 → schema_version → request_id 형식 → 중복(106) → 만료(101)
                                                      ※ cmd/scan/stop 은 만료 검사를 건너뛴다
```

중지는 늦게 도착해도 실행해야 하기 때문이다.

### 3.3 FastAPI — 중계와 발급

MQTT 를 구독해 WebSocket 으로 `{topic, payload}` 그대로 흘린다. **해석하지 않는다.** 명령 REST 를 받으면 `request_id`(UUID v4)를 **여기서 발급**하고 MQTT 로 발행한다. `scan/result` · `contact/event` 가 오면 PostgreSQL 에 쓴다.

### 3.4 프런트 — 좌표 두 번 맞추기

스캔 결과는 작업대 좌표(`workpiece_fixture`)이고 로봇 궤적은 Base 좌표다. 화면에 같이 그리려면 두 가지가 필요했다.

1. **축 대응**: ROS 는 z 가 위, Three.js 는 y 가 위다. `toThreePosition(x, y, z) → (x, z, −y)`
2. **원점 이동**: `VITE_BASE_TO_FIXTURE_MM` 만큼 옮겨 두 좌표계를 겹친다

`−y` 의 음수 부호와 원점 이동이 둘 다 있어야 맞는다. 하나만 있으면 그럴듯하게 틀린다(5.3 · 5.4).

## 5. 문제와 해결

### 5.1 모르는 값을 0 으로 저장했다 (9/22)

- **증상**: `scan/result.config.debounce_n` 이 항상 `3` 이 아니라 `0` 으로 웹에 왔고, PostgreSQL `scan_configs` 에도 0 으로 저장됐다. 화면은 "디바운스 0회"로 읽었다
- **원인**: scan_manager 가 아직 모르는 설정(`*_set=false`)을 브리지가 **기본값 0** 으로 채웠다. 계약 1장의 "미측정값은 `null`, 0을 쓰지 않는다"를 브리지가 어겼다
- **조치**: `encode_scan_config` 가 `debounce_set` 을 보고 모르면 `null` 을 싣게 했다 (PR #145 `cc64cbc`)
- **결과**: 모르는 값과 정상 0 이 API 응답까지 구분돼 나온다
- **교훈**: **"기본값으로 채우기"는 없는 값을 있는 값으로 둔갑시킨다.** 모르면 모른다고 보내야 받는 쪽이 판단할 수 있다

### 5.2 오류로 끝난 중지가 아무 통지도 못 냈다 (9/22)

- **증상**: 중지 중 작업이 `ERROR` 로 끝나면 `scan/command_result`(완료 통지)가 **아예 발행되지 않았다.** 화면의 중지 버튼이 영원히 "처리 중"으로 남았다
- **원인**: 브리지가 완료 통지를 `STOPPED` 전이에서만 냈다. `ERROR` 로 가는 경로에는 통지가 없었다
- **조치**: `_finish_stops(scan_id, success, reason, detail)` 로 두 경로를 묶고, 대기 중인 중지를 `(request_id, scan_id)` 쌍으로 들고 있다가 어느 쪽으로 끝나든 닫게 했다 (PR #145)
- **결과**: 중지가 실패로 끝나도 사유와 함께 화면에 뜬다
- **교훈**: **끝나는 길이 둘이면 통지도 둘이어야 한다.** 성공 경로만 보고 만들면 실패가 조용해진다

### 5.3 3D 화면이 좌우로 뒤집혀 있었다 (9/22)

- **증상**: 스캔한 직육면체와 로봇 궤적이 실제와 **거울상**으로 그려졌다. 치수는 맞는데 방향이 반대라 눈으로는 "그럴듯해" 보였다
- **원인**: ROS 는 z 가 위, Three.js 는 y 가 위다. 축을 옮기면서 `(x, z, y)` 로 매핑해 **부호를 빠뜨렸다.** 오른손 좌표계가 왼손이 됐다
- **조치**: `toThreePosition(x, y, z) → (x·s, z·s, −y·s)` 로 음수 부호를 넣었다 (PR #143, T36)
- **결과**: 궤적 · 접촉점 · 결과 상자가 실제 배치와 같은 방향으로 그려진다
- **교훈**: **좌표계 변환은 치수로 검증되지 않는다.** 크기는 맞고 방향만 틀리는 버그는 비대칭인 배치로만 잡힌다

### 5.4 스캔 결과와 로봇 궤적이 46 cm 떨어져 있었다 (9/22)

- **증상**: 같은 화면에 그린 스캔 결과(직육면체)와 로봇 TCP 궤적이 서로 멀리 떨어져 나왔다
- **원인**: `scan/result` 는 작업대 좌표(`workpiece_fixture`), `robot/sample` 은 Base 좌표다. **프레임이 다른 두 값을 같은 좌표로 그렸다.** 계약에 `frame_id` 가 있는데 화면이 그것을 보지 않았다
- **조치**: `VITE_BASE_TO_FIXTURE_MM` 환경변수로 원점 이동을 넣고, 값은 계약 `units-frames.md` 의 실측을 쓴다 (PR #143)
- **결과**: 두 좌표계가 겹쳐 같은 장면에 그려진다
- **교훈**: **`frame_id` 는 장식이 아니다.** 계약이 프레임을 적어 두는 이유는 화면이 그것을 보라는 뜻이다

### 5.5 내부 IP 가 공개 레포에 올라갔다 (9/22 ~ 9/23, 4회)

- **증상**: 웹 PC 내부 IP 가 목업 발행기 README · 시험 보고서 · `real.yaml` · launch 파일 주석에 그대로 커밋됐다. 공개 레포다
- **원인**: 실기 세션에서 돌아가는 명령을 그대로 문서에 옮겼다. 주소가 "설정"이 아니라 "예시"의 일부로 섞여 있었다
- **조치**: 네 곳을 각각 지우고, `bringup.launch.py` 에 `broker_host` launch 인자를 만들어 **주소를 레포에 두지 않아도 되게** 했다 (PR #163 · #179, 커밋 `0a77684`)
- **결과**: 실행 주소는 launch 인자와 `docker/.env` 에만 있다
- **교훈**: **"돌아간 명령을 그대로 붙여넣기"가 가장 흔한 유출 경로다.** 붙여넣기 전에 주소를 자리표시자로 바꾸는 습관이 필요하다. (루트 `README.md` 5곳 · `docker/README.md` 3곳은 아직 남아 있다 — 6장)

### 5.6 이름을 모르는 코드 하나가 메시지 전체를 지웠다 (9/26)

- **증상**: 계약에 새 `ReasonCode` 가 늘었는데 브리지 이름 표를 안 고치면, 그 코드가 실린 메시지가 **통째로 사라진다.** 로그 한 줄이 아니라 `scan/command_result` 전체가 안 나간다
- **원인**: `_enum_name` 이 표에 없는 값에서 `ValueError` 를 냈고, 구독 보호막(`_safe_ros_callback`)이 그 예외를 잡아 콜백 전체를 버렸다. **정작 알려야 할 코드일수록 웹이 못 받는** 구조였다
- **조치**: 표에 없는 값을 `"UNKNOWN_<값>"` 으로 내보내게 바꿨다. 숫자(`reason_code`)는 그대로 가므로 웹이 판단할 수 있다 (PR #200, 계약 v0.1.22, 이슈 #90)
- **결과**: 이름을 몰라도 소식은 끊기지 않는다. phase 2 의 `OP_WELD_PATH=5` 도 같은 PR 에서 표에 넣었다
- **교훈**: **보호막이 있으면 실패가 조용해진다.** 예외를 잡는 곳에서는 "무엇을 버렸는지"를 남기거나, 애초에 버리지 않을 방법을 골라야 한다

|---|---|---|
| 1 | **네트워크 구성도** — 두 PC 를 잇는 것은 MQTT 하나뿐 (`assets/02-network.png`) | 04-⑤ HMI · 연동 |
| 2 | **HMI 화면 캡처** — 3D 관제(관절 · 궤적 · 접촉점 · 결과 상자) + 버튼 · 로그 | 04-⑤ |
| 3 | **TR-10 네 곳 대조표** — result_store → MQTT → PostgreSQL → Spring 전 항목 PASS | 04-⑤ 또는 04-⑥ |
| 4 | **"평균 2.64 ms, 최대 312 ms"** — 평균은 기준의 1/75 인데 최대값 하나가 기준을 넘었다 (TR-05 FAIL, 숨기지 않는다) | 04-⑥ KPI |
| 5 | **좌표계 두 번 맞추기** — 축 대응(`−y`) + 원점 이동. 치수는 맞는데 방향이 틀린 버그 | 04-⑧ 문제와 해결 |
| 6 | **"이름을 모르는 코드 하나가 메시지 전체를 지웠다"** — 보호막이 실패를 조용하게 만든 사례 (#90 → #200) | 04-⑧ |
| 7 | **목업 발행기로 ROS 를 기다리지 않았다** — 계약 한 장이 있어서 양쪽이 따로 갈 수 있었다 | 04-⑤ 또는 05 |

한 문장으로: **"계약 문서 한 장을 두고 양쪽이 따로 개발했고, 실기에서 붙였을 때 프런트를 고치지 않았다."**
